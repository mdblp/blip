# Releasing the YourLoops web app (after the Terraform migration)

Once migrated (`terraform-migration-plan.md`), a release deploys two things: the static files and the
edge Lambda code. It deploys them from the blip Docker image, which stays the single artifact we ship.
The infrastructure it deploys into (bucket, distribution, certificate, DNS, the Lambda *function*) is
Terraform's, in `diabeloop-infrastructure`, and a release never changes it.

## What a release changes, and what it doesn't

| A release changes | A release never changes |
|---|---|
| Files under `s3://<bucket>/blip/<version>/` | The bucket, its policy, the OAC |
| The edge Lambda's code, as a new published version | The function's runtime, role, handler, memory |
| Which Lambda version the distribution's viewer-request runs | Origins, behaviours, aliases, certificate, cache policy, TLS |
| — | DNS records |

The distribution's origin path is a fixed `/blip`. The edge Lambda, built for one version, rewrites
`/<file>` to `/<version>/<file>`, so switching the Lambda version switches the site. Terraform ignores
that one attribute (`lambda_function_association`), so `terragrunt plan` stays clean after a release.

## Inputs

The same `blip.env` generated by `yourloops/ylp/gen_config.py`, plus AWS credentials allowed to use
the `blip-release-<prefix>` policy. The image reads:

| Variable | Used for |
|---|---|
| `APP_VERSION` | Bucket prefix, Lambda routing, `/version`, Lambda version description. **Baked into the image at build time** (`/dist/VERSION`, computed by `scripts/get-version.sh`: `<git tag>-<short sha>`, or `<short sha>` if the commit has no `v*` tag). Do not set it at deployment: `deploy.sh` fails if it differs from the image's version |
| `STACK_PREFIX_NAME` | Finds the SSM parameters `/blip/<prefix>/...` |
| `AWS_ACCOUNT` | Refuses to run if the credentials belong to another account |
| `AWS_DEFAULT_REGION` | eu-west-3 (bucket, SSM). The Lambda is always us-east-1 |
| `DOMAIN_NAME` | Post-release check, run on this host too once the domain is attached |
| `MAINTENANCE` | `true` builds a Lambda that serves the maintenance page |
| `EVIDENCE_DIR` | Where the release record is written (default `/evidence`, mount a volume there) |
| everything else (`API_HOST`, `AUTH0_*`, `BRANDING`, …) | Unchanged: `gen-lambda`, `gen-robot`, `gen-sitemap` |

Where to deploy comes from Terraform, through SSM, so nothing is copied by hand:
`/blip/<prefix>/bucket-name`, `/blip/<prefix>/distribution-id`, `/blip/<prefix>/edge-function-name`.

## Running it

```sh
docker run --rm \
  --env-file config/<env>/blip.env \
  -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -e AWS_SESSION_TOKEN \
  -v "$PWD/evidence:/evidence" \
  docker.ci.diabeloop.eu/blip:<version>
```

- `DRY_RUN=true` resolves and prints the account, bucket, distribution and function, and the number of
  file changes the sync would make, then stops before changing anything.
- `SWITCH_TO=<lambda-version-arn>` runs the switch and the checks only (fast rollback, see below).

## Steps

The order is what makes a release safe. Nothing users see changes before step 6.

| # | Step | If it fails |
|---|---|---|
| 0 | Check the credentials' account equals `AWS_ACCOUNT`; read the three SSM parameters | Nothing changed. Fix and rerun |
| 1 | Generate `robots.txt`, `sitemap.xml` and the Lambda (`gen-robot`, `gen-sitemap`, `gen-lambda`), remove `static/index.html`. `gen-lambda` fails if `APP_VERSION` is missing (`deploy.sh` takes it from `/dist/VERSION`) | Nothing changed |
| 2 | Package the single generated Lambda file as `index.js` in a zip | Nothing changed |
| 3 | `aws s3 sync static/ s3://<bucket>/blip/<version>/ --delete` | Files for a version that isn't served. Rerun |
| 4 | Upload the Lambda code, wait, `publish-version` with description `blip <version>` | A published version nobody uses. Rerun (publishing unchanged code returns the same version) |
| 5 | Read the distribution config and ETag. Stop if there isn't exactly one viewer-request association. Send the same config back with only that ARN replaced | Nothing changed |
| 6 | `update-distribution --if-match <etag>`, then `wait distribution-deployed` | ETag conflict: someone else changed the distribution (an infra apply?). Rerun once they're done |
| 7 | On the distribution's own `*.cloudfront.net` host and on `DOMAIN_NAME` (once attached): `/version` equals `APP_VERSION` (retried for about a minute), `/` returns 200 with CSP and HSTS, or 503 with HSTS in maintenance | Site is on the new version but a check failed. Investigate; roll back if needed |

No invalidation: files are cached under `/<version>/<file>`, so a new version never hits an old cache
entry. `index.html`, `config.<hash>.js` and `/version` come from the Lambda and aren't cached by
CloudFront. (Assumption V2 in the migration plan; confirmed on sandbox before relying on it.)

Every step can be rerun. After a failure, the answer is always to rerun the same image with the same
env file.

## The script

`cloudfront-dist/deploy.sh` is the image's entrypoint and implements the steps above. It runs in the
image's own layout (`/dist/static`, `/dist/lambda`, `/dist/server`) and is checked by `shellcheck` in CI.
The image carries `aws-cli`, `jq` and `zip`, and no Terraform or CDK.

The one function that touches the distribution is `switch_to`. It sends back the config it read,
changing only the viewer-request Lambda ARN, and passes the ETag so a concurrent change fails instead of
being overwritten.

## Evidence for the release record

Each run writes a folder under the mounted `/evidence`:

- `release.json`: environment, version, bucket, distribution, the previous and new Lambda version
  ARNs, the operator's identity, maintenance flag
- `distribution-before.json` and `distribution-config-sent.json`: the distribution config as read and as
  sent. They differ only in the viewer-request ARN
- `s3-sync.log`: every file uploaded or deleted

Attach it to the release in MatrixRequirements alongside the existing test results. Infra changes are
recorded separately, as the archived `terragrunt plan` in the infra repo's pull request.

## Maintenance mode

1. Set `MAINTENANCE=true` in the env file and run **the version currently in production**. The files
   are already there (sync uploads nothing), and the new Lambda answers every request except `/version`
   with the maintenance page (503, `Retry-After`, CSP, HSTS), except the mobile app links (`/.well-known/...`), which keep working.
2. To leave maintenance, run the same image with `MAINTENANCE=false`.

Each switch takes as long as a distribution deployment (a few minutes). No infrastructure change, no
Terraform.

## Rollback

- **Standard:** run the previous release's image. Its files are still in the bucket (sync uploads
  nothing), its Lambda is republished, and the switch and checks run as for any release.
- **Fast, during an incident:** `SWITCH_TO=<previous ARN from the last release.json>`. This only
  switches the distribution back, so it takes as long as a distribution deployment. It works as long
  as that version's files are still in the bucket, which they are unless someone deleted them.
- Images from before the migration contain CDK and can't deploy to a migrated environment. The
  migration release is infra-only for that reason: its predecessor is the same application.

## Housekeeping

- **Lambda versions** accumulate, one per release and maintenance switch. They are small (a single file
  with `index.html` inlined), far from the 75 GB per-region code storage limit. Prune occasionally,
  keeping the last ten. A version still associated with the distribution, or deleted less than a few
  hours ago from it, can't be deleted; that's expected.
- **Old versions' files** under `blip/<version>/` stay. They are the fast-rollback targets and cost
  little. If they need pruning one day, do it by prefix, never the current or previous version.
- **Don't run a release and an infra `terragrunt apply` on the same distribution at the same time.**
  The ETag check makes the second one fail cleanly rather than overwrite the first. Rerun it.
